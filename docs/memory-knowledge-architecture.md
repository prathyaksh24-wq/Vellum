# Memory and Knowledge Ownership

Vellum exposes one memory system and one maintained knowledge wiki. The
storage engines behind them are implementation details, not separate products.

## Canonical ownership

| Concern | Canonical owner | Supporting adapters |
| --- | --- | --- |
| Chat history | `data/ui/conversations.json` through `/api/conversations` during migration | Knowledge Core shadow source, Obsidian conversation projection, FTS5 index |
| Durable memories, status, settings, summaries | Memory Orchestrator SQLite store | FTS5, Chroma memory cards, Honcho, optional provider extensions |
| User-readable conversation archive | `Vault/Agent/Conversations` | Generated from canonical chat history |
| User-readable memory snapshots | `data/memory/USER.md`, `data/memory/MEMORY.md`, and structured Obsidian cards | Generated by Memory Orchestrator/Dreaming |
| Maintained reference knowledge | `Vault/Knowledge` through Knowledge Wiki during migration | Knowledge Core derived insights; Obsidian becomes the Karpathy-style projection |
| Raw imports | `Vault/Library` during migration | Knowledge Core content-addressed source versions; Obsidian remains an optional surface |

The frontend calls only stable `/api/memory/*`, `/api/conversations/*`, and
`/api/knowledge/*` contracts. It must not choose between Knowledge Core SQLite,
Obsidian, FTS5, Chroma, Honcho, or provider extensions.

See `docs/PERSONAL_INTELLIGENCE_ARCHITECTURE.md` for the additive migration and
cutover gates. Until those gates pass, the current owners in this document
remain active and the Knowledge Core operates in shadow mode.

## Retrieval flow

1. The process-wide Memory Orchestrator builds the bounded memory packet.
2. SQLite supplies summaries and saved memories; FTS5 supplies relevant past
   turns; Honcho and enabled extensions may add context.
3. The Knowledge Wiki contributes only lightweight page references. Page bodies
   are read with `knowledge_wiki` on demand, so knowledge is not duplicated into
   personal memory.
4. Current conversation context always wins when older memory conflicts.

## Write flow

1. `/api/conversations` saves the canonical thread.
2. The background learner indexes the turn and extracts pending durable memory.
3. Dreaming promotes, merges, summarizes, archives, and audits memory changes.
4. The Obsidian exporter updates one human-readable note per conversation.
5. Knowledge pages change only through explicit wiki upsert/approved ingestion.

Legacy `Agent/Queries` and `Agent/Responses` files are migration inputs, not
canonical memory. New runtime behavior must not create timestamped per-turn
notes in those folders.

## Recovery

Knowledge Core backups contain the SQLite database, content-addressed blobs,
and a checksummed manifest. Restore is an offline maintenance operation: stop
Vellum, verify the archive, and use the explicit `RESTORE_KNOWLEDGE_CORE`
confirmation token. A verified pre-restore rollback archive is always created
before the live database and blob generation are replaced.

## Honcho portrait scope

Honcho dialectic retrieval uses an explicit session allowlist from the canonical
conversation lifecycle. Chats removed locally cannot re-enter the portrait through
a stale Honcho representation. Chats explicitly introduced as a temporary
demonstration or limited to that chat are excluded from the portrait; their ordinary
conversation context remains available through the existing history owners. Empty
or unavailable canonical history fails closed. The allowlist returns directly stated
conclusions from those sessions, rather than unrestricted cross-session derivations.
Posting and other one-off X commands are not durable user-profile facts.
