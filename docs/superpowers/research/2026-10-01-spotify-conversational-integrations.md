# Spotify conversational integrations and implications for Vellum

Verified against official sources on 2026-10-01. This is research and design guidance, not an implementation or a playback test.

## What ChatGPT actually does

Spotify is an official app in ChatGPT. The documented experience accepts songs, artists, playlists, moods, themes, and conversational context; Spotify supplies personalized picks. Connecting an account is opt-in. Premium users can receive personalized track selections, while the launch description routes taps to Spotify for listening. [Spotify announcement](https://newsroom.spotify.com/2025-10-06/spotify-personalized-prompts-chatgpt/).

The same announcement's March 23, 2026 update adds audio previews and full podcast episodes inside ChatGPT without login. It does **not** announce full-length music playback inside ChatGPT. OpenAI's current product page still describes opening Spotify to play, plus conversational playlist creation, editing, naming, and suggestions informed by listening preferences. [Spotify update](https://newsroom.spotify.com/2025-10-06/spotify-personalized-prompts-chatgpt/), [OpenAI product page](https://chatgpt.com/apps/spotify/).

OpenAI describes ChatGPT apps as Apps SDK integrations built on MCP, with app-defined interfaces and logic connected to developer backends. Spotify was a named pilot partner. These are public platform facts; Spotify's specific tool schemas, backend endpoints, recommender implementation, playback internals, and negotiated permissions are not disclosed by these pages. Do not claim it simply uses the public Web API or Web Playback SDK. [OpenAI app announcement](https://openai.com/index/introducing-apps-in-chatgpt/).

User-observed capability (not independently inspected): the connected ChatGPT Spotify app exposes three write tools described as "generate from playlist", "remove from library", and "save to library", and three read tools described as "search", "get current tracks", and "fetch". The user reports creating playlists, finding songs, and fetching current songs. The public launch article is not an exhaustive current tool inventory. Exact schemas, descriptions, device parameters, and the meaning of "current tracks" remain unverified; this label does not establish a currently-playing endpoint. No explicit playback-control tool appears in the reported names. Reading playback state or issuing a partner-server operation would not, by itself, establish where full-song audio plays.

Useful architectural inference: keep conversational intent, music selection, and playback separate. The sources support that division at the product level, but do not expose the internal implementation.

## Public permissions versus partnerships

The public developer policy prohibits voice-control assistants, analyzing Spotify content/service to build user profiles, and ingesting Spotify content into AI models, beyond model training alone. Commercial streaming also has restrictions. Typed input avoids the voice-specific issue; it does not automatically resolve the remaining boundaries. Premium, personal use, local inference, user consent, or an MCP wrapper are not documented exemptions. Official partnerships establish that those integrations exist, not what permission Vellum has. Obtain Spotify clarification for uncertain features rather than inventing partner-contract terms. [Developer Policy, III.3/13/14 and IV](https://developer.spotify.com/policy).

Design implication: parse the user's own words into a typed command. Keep API-returned metadata, artwork, histories, and track analysis outside the model unless appropriate permission is established; display results directly in the UI. This is a proposed boundary, not a blanket compliance guarantee.

## Applying the pattern to Vellum

- **Title-only request:** extract `play_track(title="Last Christmas")`. Search and resolve in deterministic integration code; optionally use a user-declared preferred version. Do not assume every title has one answer or that search order guarantees the original recording. Ask only when candidates remain genuinely ambiguous. Spotify supports track/artist search filters. [Search reference](https://developer.spotify.com/documentation/web-api/reference/search).
- **My Hindi playlist, shuffled:** resolve among the user's owned/followed playlists rather than public playlist search. Proposed implementation: choose a playable initial item randomly and start the verified playlist context with that offset on the chosen device; enable shuffle and confirm actual state. Starting at a random item avoids always playing track one before shuffle takes effect. Spotify warns execution order across Player endpoints is not guaranteed, so issuing requests sequentially alone is insufficient. [User playlists](https://developer.spotify.com/documentation/web-api/reference/get-a-list-of-current-users-playlists), [playback](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback), [shuffle](https://developer.spotify.com/documentation/web-api/reference/toggle-shuffle-for-users-playback).
- **Mood and memory:** a tentative conversation-based suggestion, such as "Would your relaxing Hindi playlist help?", is preferable to silently diagnosing emotions or starting audio. User-authored memories such as "this song helped me last time" have different provenance from inferred Spotify listening profiles. Preserve that distinction and existing local memory ownership. Do not treat it as an exemption: automatic enjoyment inference from skips, history, or repeated listening needs Spotify clarification under III.13/14. [Policy](https://developer.spotify.com/policy).
- **Long-term reliability:** use a persistent player, fresh tokens, explicit readiness/reconnection states, command deadlines, and state reconciliation. The SDK requests a token on connect and expiry, with access tokens lasting at most 60 minutes. Respect `429 Retry-After`; avoid duplicate non-idempotent commands. Test token cycles, restart, sleep/wake, network interruption, navigation, and device switching. Sustained usability means recovery across sessions; no public source guarantees an uninterrupted months-long session. [SDK reference](https://developer.spotify.com/documentation/web-playback-sdk/reference), [rate limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits).

Vellum-specific proposed order: prove protected audio playback in the packaged desktop shell; repair and verify the existing Spotify connector; then add typed intent and carefully scoped user-authored preferences. Extend existing plugin, capability, and memory owners rather than introducing parallel runtimes. This note does not validate the current connector bugs or establish live playback compatibility.
